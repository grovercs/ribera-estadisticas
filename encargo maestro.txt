# PROYECTO: PUBLICACIÓN EN NETLIFY DEL PANEL DE ESTADÍSTICAS DE LOGÍSTICA RIBERA

## OBJETIVO

Tenemos actualmente una aplicación de estadísticas de Logística Ribera funcionando en local.

La aplicación consulta datos del ERP de Ribera, cuya base de datos está en un SQL Server dentro de la red local de la empresa.

El objetivo es convertir esta aplicación en una solución web accesible desde Internet mediante:

- Netlify
- Next.js
- TypeScript
- Supabase
- PostgreSQL
- Supabase Auth
- Supabase RLS
- Tailwind CSS
- shadcn/ui

La aplicación de estadísticas será principalmente de SOLO LECTURA.

El SQL Server local debe continuar siendo la FUENTE DE VERDAD del ERP.

NO se debe exponer SQL Server directamente a Internet.

---

# REGLA CRÍTICA: NO EMPEZAR REESCRIBIENDO

Antes de crear código nuevo debes estudiar exhaustivamente la aplicación existente.

La aplicación actual ya:

- se conecta correctamente a la base de datos de Ribera;
- ejecuta consultas SQL reales;
- obtiene estadísticas;
- conoce tablas y relaciones del ERP;
- tiene lógica de negocio ya descubierta;
- posiblemente dispone de gráficos, KPIs, clientes, ventas, productos, stock u otros datos.

NO debes volver a descubrir desde cero información que ya exista.

NO debes sustituir consultas SQL que funcionan simplemente por crear otras nuevas.

NO debes inventar nombres de tablas, columnas, relaciones o reglas de negocio.

Primero:

1. inspecciona el repositorio completo;
2. identifica cómo funciona actualmente;
3. identifica la conexión existente al ERP;
4. identifica todas las consultas SQL utilizadas;
5. identifica qué información muestra cada pantalla;
6. identifica qué transformaciones se realizan después de las consultas;
7. identifica qué componentes visuales ya existen;
8. identifica qué partes podemos reutilizar.

Después presenta un Implementation Plan.

## Una precisión importante

Hay una cosa que **Gemini debe comprobar** y no debemos imponerle de antemano: me has mostrado ahora que la aplicación de estadísticas parece hablar con un **SQL Server**, mientras que en otras partes del proyecto Ribera habíamos hablado de un sistema legacy con **MySQL**. Puede ser perfectamente que sean **dos bases distintas**, o que el panel estadístico esté conectado a otro ERP.

Por eso he puesto que **primero determine el motor real y las consultas reales**. No quiero que Gemini empiece una migración suponiendo que es MySQL o SQL Server y termine conectando la arquitectura a la base equivocada. 

Y sí: para esta fase yo **no le pediría todavía que programe nada**. Que nos entregue primero ese informe de auditoría. Cuando te lo dé, me lo pasas y yo lo reviso contigo antes de que Gemini toque Supabase.
